# 技能设计与验收

## 职责划分

每个技能对应一种可以单独提出的请求。`discover-workflow` 按当前目标和阶段查找实际可用的技能，推荐下一步。`implement` 根据实际工作选择直接实现或多任务调度；只有涉及任务依赖、委派或集成时才加载调度流程。输入来自规格并不意味着需要拆成多项任务。

`triage` 核实原始请求、查重并判断实施就绪程度。`to-spec` 说明要实现什么、如何验收，并在交付规模与依赖需要时将已确定的规格拆成可执行任务；也可直接拆分已有成熟规格。小需求交付规格即可，用户只要求规格时遵循其范围。`maintain-tasks` 依据决定和证据维护任务、依赖及状态，tracker 工具负责结构校验。分类、分诊和执行状态分别表达不同事实，保持对应关系。

`improve-codebase-architecture` 调查值得推进的整体改造方向，比较方案及迁移代价。`review-code-design` 核实指定范围的设计问题和简化机会。前者可使用后者的发现作为输入，沿已有证据补查；共同设计方法由 `codebase-design` 维护。重要方案比较包含同尺度前后图，复杂报告复用 `present-report` 的阅读层次。

`prototype` 以可运行实验检验设计假设，`research` 以来源调查解决事实与选择的不确定性。`handoff` 准备交接，`recover-work` 核实现场并继续工作，即使交接材料缺失也能处理崩溃或上下文丢失。

`present-report` 将调查结果整理成报告，调查本身由相应任务负责。`humanizer` 调整措辞，保留事实和要求的强弱。文档维护检查内容与引用是否准确；`clean-workspace` 统一工作区整理入口，按请求处理无用文件、未提交修改分组提交或已有提交历史整理，共用盘点、归属、分组和验证判断。

编写技能时，说清目标、适用范围、默认步骤、分支选择和完成标准。模型依据证据在明确路径间选择，涉及范围或投入取舍时交用户决定。特殊情况需要的方法放在参考文件中，遇到时再读取。结构化规格、独立调查、独立审查和方案比较提供一致的工程过程，展开程度由任务决定。公共规则集中维护，逐项只补充差异，已保存正文不在交付回复中重复。发现执行问题后，先从会话判断指令、工具、环境和自动检查的责任，再修改对应内容并对照验证。

## 项目接入与交付

`setup-project` 建立统一 Gnosis 模式：本地任务固定为 `issues/`，术语表为 `GLOSSARY.md`，ADR 为 `docs/adr/`，规格和报告为 `specs/`、`reports/`，不通过配置覆盖。配置记录 tracker 类型、远程字段映射、验证入口与 Git 偏好，远程 tracker 继续可用。现存文件不自动移动。已有项目先盘点再预览迁移，确认后应用，保留旧记录及其历史引用。普通分析可在接入前完成，持久工作流接入时统一语义。

Git 完整交付在获得相应授权后连续执行。先盘点未提交内容并确认处理，选择 base，小修沿当前分支，中大修改采用工作分支，验证和独立审查后提交、合并回 base。关闭指 tickets、spec 和验收清单的证据驱动更新；父规格另行检查整体验收，未满足的项目保持开放。分支或 worktree 的清理另按用途和授权判断。

`implement` 实施前核对用户已确认的迁移与兼容策略，缺失时先调查实际影响，再集中询问，等待答复后开展依赖该决定的实现。已有适用决定直接沿用，部分明确时只补问缺口。允许破坏性变更时同步更新当前调用方，旧版本兼容或专门拒绝逻辑须有明确需求。

## 技能依赖与共享文件

技能可以依赖其他技能，必要依赖应在入口和安装说明中写清，安装时一起选择。`grill-with-docs` 依赖 `grill-me` 的访谈流程和 `domain-modeling` 的术语与 ADR 方法。缺少必要依赖时说明缺口；可选辅助技能缺失时，继续完成主任务。不能假定安装工具会自动解析正文中的依赖。

共享规则在 `shared/` 修改，构建时复制到需要它们的技能目录中的 `references/`。技能内部的特殊流程放在自己的参考文件中，按条件读取。保留必要的参考副本，不为每个跨技能依赖再写一套兜底实现。

已有测试的维护方法统一放在 `shared/test-maintenance.md`。`implement` 与 `tdd` 在调整旧测试或迁移覆盖时进入，`codebase-design` 在新接口替代旧结构时规划迁移，`code-review` 核对需求依据、原风险的覆盖去向和验证证据。只处理本次变更及受影响边界，普通任务不扩展为测试库治理。

技能默认由 Codex 自动发现，描述应写清适用的请求。例如，访谈和报告技能只在用户有相应意图时使用。其他平台对 `disable-model-invocation` 的解释不能直接套用；若要改成仅允许手动调用，需使用目标环境支持的元数据，并验证实际行为。

## 文件保留与清理

仍有用途的记录继续保留；已结束使用但有历史价值的记录可以归档。文件是否有用，需要结合内容和使用情况判断，不能只看目录名、修改时间或 Git 状态。

创建临时文件的任务负责收尾。`clean-workspace` 的文件分支处理多个任务留下的残余文件，直接删除确认无用的内容，用途不明时保留并核实。其 Git 分支按意图与依赖分组，保护混合 hunks、原有暂存边界和其他任务改动；历史改写先核实准确 base/range、共享状态、dirty state 与恢复入口，再验证最终内容树及受影响的中间提交。merge 历史须明确保留拓扑或获授权展平。清理文件不自动提交，授权提交不自动改写历史，推送与远程历史替换另需相应授权。

迁移先展示路径、状态和引用的对应关系。未知状态或无法保留的引用会阻止自动迁移。源记录保持不变；完成复制后，还需确认 tracker 已切换。旧位置如何处理按已确认的方案执行，迁移授权不包含清理授权。

## 验收场景

| 场景 | 预期行为 |
| --- | --- |
| 小范围实现 | 运行相关检查，不要求建立 tracker、运行全量测试或自动提交 |
| 某项任务被依赖阻塞 | 保留依赖，继续不受影响的任务；集成后验证整体结果 |
| `.scratch` 中有未完成任务 | 保留任务记录；用途不明的文件先询问，确认无用的临时文件直接删除 |
| 混合未提交修改并已有无关暂存 | 按意图与依赖分组，精确处理 hunks；检查每次完整暂存差异，保留无关内容与暂存边界 |
| 已授权整理并提交当前修改 | 完成已授权分组和提交，不重复确认，不自动 squash 或推送 |
| squash 或重排已有提交 | 核实准确范围、共享状态和恢复 ref，保护 dirty state；最终树等价且受影响的中间提交满足依赖 |
| 带 merge 的历史或整理发生冲突 | 先选择拓扑策略，保留 merge 解决与冲突现场，不默认展平或丢弃未知提交 |
| 中断后留下有效改动 | 核对后继续，不因测试失败重置整个工作区 |
| 按需安装技能 | 包内参考可读，必要依赖明确；缺少可选技能时仍能继续工作 |
| 访谈与文档记录 | `grill-with-docs` 复用 `grill-me`，普通访谈不自动创建记录 |
| 更新报告 | 沿用工作区内的报告路径，图示有证据支持，允许使用 CDN |
| 润色规范文字 | 保留否定、条件和引用，不改变必须、建议、可选的含义 |
| 迁移 tracker | 两种来源均可预览，对应关系明确；有未知项时停止自动应用，源文件字节不变 |
| 多角色功能形成规格 | 用户故事表达角色、诉求和收益，关键故事有行为与验收对应；小修复不凑长列表 |
| 小修或纯技术规格 | 直接说明问题、行为与验收，不强制用户故事、编号或空栏目；仍检查来源与范围覆盖 |
| 选择规格验证接口 | 说明稳定行为接口、覆盖和重要盲区；有实质取舍时说明依据，不为减少接口数量遗漏风险 |
| 工单交给新会话 | 单票包含目标、必要上下文、依赖产物与验收入口，引用可访问，不依赖原会话记忆 |
| 多项任务共享完成标准 | 公共规则集中说明并可由工单引用，列表不逐项复制相同后缀；各票独有验收不丢失 |
| 已保存任务或报告 | 交付入口与关键结果，不重复全文；用户要求完整列表或正文时提供 |
| 多个架构候选 | 简列候选及证据，仅展开值得比较或推进的项，关系图按理解需要提供 |
| 单项或无发现的评审 | 有发现时紧凑交代证据和行动，无发现时说明结论与实际限制，不回显检查清单 |
| 难复现缺陷 | 按症状选择反馈方法，检查信号能否区分前后；未复现时保持假设状态并继续可行调查 |
| 设计审查发现可疑结构 | 用真实调用和变更后果判断，结构相似本身不足以认定缺陷 |
| 精简技能 | 关键动作、输出要求及覆盖检查仍能找到，用同一场景比较精简前后行为 |
| 多个当前可回答的决定 | 访谈按内部决策树一次提出多个独立问题，依赖答案的问题留到下一轮 |
| 已有难维护结构阻碍功能 | 切票比较直接切片、准备性重构、扩展迁移收缩和联合交付，按收益与验证选择 |
| 分诊就绪但前置未完成 | 保留 ready-for-agent 的信息就绪含义，执行者依据真实依赖等待 |
| 指定代码设计审查 | 检查真实问题及大胆简化提案，整体架构调查复用发现并展开重要方案 |
| 独立审查自身实现 | 提供事实材料给未参与实现的新上下文审查者，主代理核实和整合发现 |
| 极罕见缺陷无有效进展 | 提交证据、成本和选项供用户决定，继续无依赖工作，核心未验收条件保持开放 |
| 新接口替换旧结构 | 映射旧测试保护的行为，验证新测试后删除重复浅层测试，保留高价值低层覆盖 |
| 重构后仅 mock 调用次数断言失败 | 核实调用次数是否有真实契约；无此契约时迁移实现耦合断言，不机械恢复旧调用结构 |
| 需求明确废止旧行为 | 按已授权决定更新或删除旧测试，验证新行为及相关边界，不为废止行为补建替代测试 |
| 两条测试看似重复，其中一条保护并发问题 | 比较错误路径、边界及运行环境，保留独特的并发保护 |
| 更新快照掩盖未授权的输出变化 | 指出行为回归，不能仅凭快照更新后全绿接受变化 |
| 测试偶发失败 | 调查环境与反馈可靠性，不以跳过、提高超时或重试代替原因判断 |
| 小修改且旧测试无需调整 | 沿用最小验证路径，不扩展为测试库治理 |
| 有或没有交接材料的恢复 | 均核实当前差异、进程、所有权和证据；资料缺失时从现场建立可确认的上下文 |
| 完整交付关闭记录 | 根据证据更新 checklist、tickets，再验证父 spec 整体条件，区分本地与外部实际状态 |
| 实验与临时产物收尾 | 实验报告输入、结果和限制，执行者处理本次临时资源，保留仍需复核的证据 |

验收时应说明哪些结论来自静态推演、哪些经过隔离试运行、哪些已在真实项目中验证。脚本测试可以重复执行，但通过脚本测试不代表这些场景都已通过实际模型验证。
