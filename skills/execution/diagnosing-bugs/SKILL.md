# 以证据定位问题

先区分用户观察、预期行为和当前推断。诊断范围由请求决定；诊断本身不授权修改生产配置或添加线上探针。

## 建立反馈信号

读取相关实现、配置、近期变化及已有术语和决策，找到最接近症状的验证入口。优先使用现有测试、命令、请求回放或最小场景；只读取代码也可以帮助设计探针。

反馈信号应能捕获用户报告的具体异常。记录触发输入、环境、实际输出和预期结果，逐步缩小仍能触发问题的条件，避免为追求最小样例丢失实际触发问题的环节。

偶发问题记录观察次数、失败率和环境，控制关键变量，报告统计局限。性能问题先建立可比较的基线，使用计时、剖析或查询计划区分成本来源。

## 检验原因

- 根据证据提出可证伪的解释，写清“如果成立，应观察到什么”。有多个合理解释时比较它们，数量由证据决定。
- 选择能区分解释的最小探针，例如边界日志、断点、输入差异或局部对照；应能判断每次变动对结果的影响。
- 根因需要直接观察或对照支持，并解释已知症状。只符合直觉的解释标为假设。
- 无法复现时继续可行的只读定位，区分已排除项、候选原因和证据缺口。需要用户环境、脱敏材料或额外权限时给出具体需求；不能把未复现包装成已确认根因。

保存日志、trace、复现材料或临时探针前，读取 [产物约定](references/artifacts.md)。输出与留存材料只包含必要的脱敏证据。

## 修复或交接

仅诊断的任务在结论、证据和下一步明确后交付。已授权修复时，在正确边界修改源头；适合长期保留的复现转为回归测试，验证其能检测原问题，再检查原始场景和受影响边界。缺少合适测试入口时使用实际复现证据，说明保护范围。

完成时报告症状、确认的原因或假设、复现与对照结果、修复状态和剩余风险。移除本次临时探针，保留仍有用途的材料。未观测到改善的修复不能宣称解决问题。
