# 防御代码与契约

每处防御应能说明失败场景、责任归属和失败后的行为。依据来自业务契约、真实调用、信任边界、运行环境或故障记录；安全威胁无需等到事故发生才处理。

## 是否必要

沿支持的调用路径判断防御是否会触发。内部代码应使用类型、构造方式或入口校验已建立且仍有效的保证，删除不增加保证的重复处理。假想的未来调用方式不足以支持新增兜底；类型声明也不能保证外部数据可信。

考虑删除防御后能否更早暴露契约错误或直接传播原始错误。重复责任集中到负责的边界；接口含糊或构造失控造成的无效状态，优先在源头修正。无恢复需求的重试、掩盖错误的兜底都可以建议删除。

新增防御须说明现有机制未覆盖的失败路径及影响。日志、开关和包装层也需要具体用途。用途不明时保留为待核实项，既不据此删除，也不继续加固。

## 失败与恢复

- Fail fast：契约或不变量被破坏时，在最接近来源且能识别问题的位置停止受影响的操作，保留原因和上下文。停止范围由业务契约决定，拒绝一条记录未必需要终止整批任务或服务。
- 按可信程度校验外部输入、持久化读取和第三方响应。数据被修改、跨进程传递或权限变化后，重新判断原有保证是否有效。开发期断言可以帮助暴露契约破坏。
- 区分正常缺失、无效输入和系统故障。默认值或空集合须符合契约，捕获异常不能伪装成功，日志不能替代正确返回或错误传播。
- 重试须有可恢复的失败、停止条件及幂等保证或重复副作用处理。降级结果须符合契约且可观测；兼容分支应对应实际支持的调用者或版本。
- 安全检查失败时按安全契约拒绝操作。Fail fast 不构成删除鉴权、输入校验或纵深防御的理由，正常业务分支也不应一律当作异常。

## 责任与抽象

高内聚让同一规则的定义、修改和验证集中；低耦合让调用者无需掌握内部状态、特殊值或操作顺序。重复校验可能保护不同边界或时间点，去重前先核实责任。

接口应封装模块负责的错误处理、顺序和状态约定。调用者反复补默认值或恢复步骤时，检查接口与责任划分。移除转发层前，判断复杂度会消失、集中还是散落到调用方。

通过类型、构造方式和受控状态转换限制无效状态，运行时检查它们无法保证的条件。同一约束保留明确的权威定义，避免实现分叉；去重时保持独立领域和信任边界的分离。

通用接口、兼容层和策略分支应有实际变化、风险隔离或测试需求。以调用方式和维护后果判断收益，语法形式、防御代码数量、实现数量、层数、行数或模式名称都不足以单独证明问题。
