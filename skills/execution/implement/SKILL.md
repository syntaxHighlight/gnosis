# 实现与交付

交付用户指定的工作，使行为变化与验收证据对应。输入可以来自对话、规格或 tracker；不要求特定工具、其他 skill 或持久任务文件。

默认按确定范围、实施验证、独立审查、交付关闭的顺序推进。单项工作直接执行；有多项可独立验收的工作，且需要依赖调度、冲突协调或跨任务集成时，读取 [多任务调度与集成](references/multi-task.md)。输入名为“规格”或 spec 本身不触发任务图。

## 确定交付边界

- 读取请求、引用资料、最近的项目规则及相关实现，确认目标、非目标和可观察的完成条件。已有任务需同时读取其依赖与上层目标。
- 用现有代码核实前提。已实现的部分按实际结果验收；前提错误或条件互相冲突时说明影响。能从上下文确定的日常细节自行处理，只有实质改变结果的缺口需要澄清。
- 先查看工作区已有改动，识别需要保留的内容。共享接口、schema、迁移、依赖或跨模块状态需要扩大修改面时，先说明影响并确认仍在授权范围。

用户要求提交、分支交付或完整交付时，读取 [Git 交付流程](references/git-delivery.md)。先盘点未提交内容并确认处理方式，再确定 base 和工作分支；完整交付已获授权后连续执行约定步骤。项目配置帮助选择流程，实际提交、合并和外部关闭仍以本次授权及项目规则为依据。

## 实现与验证

新增或调整判空、默认值、异常捕获、重试或兼容逻辑时，读取 [防御与设计原则](references/defensive-design.md)，明确失败场景及责任归属。

1. 找到产生行为的源头及项目已有抽象，选择能满足条件的最小完整改动。默认推荐使用 `tdd`，按行为逐项红—绿—重构；已有测试先证明能检测目标问题。纯文档、生成产物或难以自动断言的任务采用能观察结果的检查，并说明保护范围。缺少 TDD 技能时仍可按项目现有方法完成验证。
2. 修复与改动直接相关的失败。额外问题不混入当前交付；需要持续跟踪时，沿用现有记录方式。
3. 从被改包的清单、文档和检查配置确定验证范围。优先运行能覆盖行为及受影响边界的检查；通过后，仅因新失败或未解除的风险扩大检查。小而可逆、且测试只会复述实现的修改可以使用直接检查。
4. 阅读完整差异，检查范围、原有改动和错误路径。记录本次创建的临时探针、日志、隔离目录及进程的用途与位置；收尾时处理已无用途的资源，持续需要的证据进入现有记录。

默认由未参与实现、使用新上下文的审查者检查变更，可调用 `code-review`。提供目标、需求来源、固定差异范围、项目规则及验证证据，让审查者独立形成结论；主代理核实发现并协调修复。规范与需求视角均需覆盖，权限、资金、数据完整性、迁移或广泛兼容性变更增加相应专项视角。代理数量随风险和可独立审查的范围决定。协作不可用时自行核查关键边界，报告独立审查缺口。修正后补查受影响部分。

需要写入或更新任务状态时，读取 [tracker 约定](references/tracker.md)；需要保留复现、日志或交接材料时，读取 [产物约定](references/artifacts.md)。没有持久记录需求时直接在对话交付。

## 交付与关闭

将验收条件逐项对应到实际证据，满足的条件更新勾选；尚待用户判断、受阻或未验证的条件保留原状态并写明缺口。完成实施与约定的集成验证后，按授权关闭对应 ticket。spec 及父目标还需检查自身的整体条件，不能仅因所有子票关闭就自动完成；取消范围需先有明确决定并说明影响。

关闭记录使用 tracker 原有方式，保留规格、验收结果和历史引用。远程关闭须处于相应授权范围；只有本地记录得到更新时，报告实际完成的位置。Git 分支和临时资源的清理另按用途处理。

## 完成标准

- 每个验收条件都有通过证据，或明确列为未验证、受阻或待用户判定；后者不能被报告为已完成。
- 相关检查通过，或检查无法运行的原因与实际风险已说明；任务要求的实现未因提前汇报而中止。
- 报告行为变化、关键位置、实际验证结果和剩余项，以及 tickets、spec 和验收勾选的实际更新结果。
- 完整交付模式下，约定的提交、合并、集成验证与关闭已完成；遇到阻碍时保留现场，明确剩余动作和解除条件。其他模式按其授权边界交付。
