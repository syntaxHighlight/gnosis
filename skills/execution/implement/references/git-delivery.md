# Git 交付流程

先读取项目 Git 规则，并结合用户请求确定交付范围。用户已授权完整交付时，按以下顺序持续完成；仅授权代码修改时先完成实现和验证，再交付当前成果及后续所需操作。配置中的模式与 base 表达项目偏好，授权来自用户请求和有效项目规则。

## 准备工作区与 base

1. 检查当前分支、工作树、暂存区和相关差异，区分本次任务与已有修改。存在已有未提交内容时，展示受影响范围，询问是原地保留、独立提交、使用 `git stash` 临时搁置，还是采用用户指定的处理方式。执行已确认方案后记录可恢复的入口。
2. 确定 base，优先使用用户指定或项目已确认的分支；有多个合理目标或当前分支已有其他任务时询问。核实准确分支及起点，避免将无关提交带入交付。
3. 边界清楚、低风险的小修留在当前分支；跨模块行为、重要契约、迁移、较大结构调整或需要隔离的工作创建任务分支。按风险与工作关系判断规模，文件数量仅作辅助。工作分支基于已确认的 base；存在尚未处理的已有改动时等待相应决定。

工作区处理应保留有效成果。选择性暂存本次修改，同一文件混有其他内容时按修改范围处理。未知归属、冲突或操作失败先核实，保持现场可恢复。

## 审查、提交与集成

完成行为验证和独立审查，修复可靠发现，检查最终暂存差异，按项目约定提交。仅将本次授权内容纳入提交。

工作分支交付时，将当前 base 的变化纳入集成判断，再按约定合并回 base。冲突按需求和双方变更处理，不能通过丢弃未知改动使合并通过。小修已在交付分支完成时直接验证该结果。

合并后核对最终差异与工作区状态，运行能覆盖新集成风险的检查，复用仍适用的单项证据。若项目通过 PR 集成，遵循其评审与合并方式；创建或合并远程 PR、推送及发布均须处于对应授权范围。

## 关闭与收尾

按主流程关闭已验收的 tickets、spec，并勾选确已满足的内部条件。合并成功本身不能证明所有业务验收成立。

关闭后检查本次更新的任务和规格是否纳入版本控制。需要入库的收尾改动按已有完整交付授权提交，并沿项目分支或 PR 方式集成到交付目标，核实最终版本已包含真实关闭状态；先前的实现提交不能代替这些记录的提交。仅因文档收尾产生的新提交执行对应格式与引用检查。项目明确不入库的本地记录或远程 tracker 状态，报告其实际存放位置。项目要求额外的合并批准时保留待集成状态和入口。

清理由本次创建、已完成用途的工作树、临时分支与运行资源，先核实其中没有未交付改动。保留仍有用途的规格、任务和证据。报告交付分支、提交或合并结果、验收与关闭情况，以及剩余未提交内容。
