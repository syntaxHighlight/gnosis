# 多任务调度与集成

用于多项工作需要依赖调度、冲突协调或跨任务集成的交付。每项工作仍按 [实现与交付](../SKILL.md) 的边界、实现和验证要求执行。

## 建立任务图

读取请求、规格、现有任务、项目规则和工作区状态，确定本次授权覆盖的任务集合及整体完成条件。已有任务结构优先；仅在缺少可执行拆分时，按可独立验证的结果拆分。任务图可以保留在当前执行上下文中，不要求创建任务文件。

区分两种关系：`depends_on` 表示前置条件，`parent` 表示目标归属，不能把归属当成依赖。检查缺失引用、依赖环、父子关系环和相互冲突的验收条件。选择当前前置条件已满足的任务；依赖通常须已完成才满足，取消不自动解除下游依赖，应重新判断要求。依赖受阻时继续不受影响的分支。

需要写入或更新任务记录时，读取 [tracker 约定](tracker.md)。本地任务固定放在 `issues/`；项目配置 `.gnosis/project.json` 可用时，从中读取 tracker 类型和其他约定。缺失时先读取已有记录，不要求初始化工具链或自动迁移。

## 调度与集成

- 为每项工作提供目标、修改边界、相关上下文、前置结果、验收条件和验证方式。执行者报告差异、证据、阻塞项及对下游的影响。
- 按依赖、文件冲突和可用工具决定并行程度。只有边界独立且允许委派时才分派；无法委派时顺序执行同一任务图。调度不依赖固定代理数量。
- 在共享工作区明确文件所有权；确有隔离需要时采用项目支持的分支或 worktree。保留其他人的改动，不能用重置解决所有权不明的冲突。
- 每项完成后检查差异和有效证据，再按实际结果更新状态，重新判断哪些任务可执行。接口或行为偏离规格时先处理偏差，不能改写验收条件迁就实现。
- 单票达到条件后勾选相应验收并按授权关闭，记录其验证入口及对下游提供的结果。遇到罕见缺陷或用户待定事项时，只阻塞实际依赖它的分支，继续其余可交付工作。
- 集成后验证跨任务边界和整体行为。复用仍有效的单项证据，只补充集成风险所需检查。

交接、隔离目录或中间证据需要留存时，读取 [产物约定](artifacts.md)。只清理由本次创建且已无用途的运行资源；有未交付改动的 worktree 继续保留。

## 完成标准

授权范围内的任务均有真实结论，整体验收条件有证据。上层目标只有在相关子任务已完成或已明确取消、且自身条件满足时才能完成；取消的工作对整体目标或规格有影响时必须说明。按整体证据更新 spec 及父目标的验收勾选和完成状态，报告已交付范围、集成结果、关闭情况、受阻任务及其解除条件。分支、提交、PR、发布和外部状态变更遵循主流程已确认的交付模式及授权。
