# 变更审查

以可复现的变更范围为依据，报告会影响正确性、兼容性、安全、性能或维护的实际问题。默认只读；修复和发布需在相应授权范围内。

## 确定证据

识别用户指定的提交、分支、PR 或工作区范围。分支分叉后的改动使用 merge-base 比较；指定精确提交区间时遵循区间；工作区审查同时考虑已暂存、未暂存及相关新文件。记录解析后的基点与当前状态，避免引用变化导致审查范围改变。不能可靠推断范围时再询问；空 diff 如实报告。

读取改动相关的最近项目规则、贡献规范及上下游调用。从用户材料、任务引用或现有规格寻找需求；需要跟踪器时读 [跟踪约定](references/tracker.md)。缺少需求资料仍可继续审查正确性和规范，但应说明需求符合性无法完整判断，不能以推断代替规格。

## 分开核对，统一证据质量

默认由未参与实现、使用新上下文的审查者执行。主代理提供固定的变更范围、项目规则、需求来源、代码入口、验证结果和已确认约束，初始任务材料以事实为主，让审查者独立形成结论。实现者负责回应和修复，主代理核实发现、协调分歧并验收修复。

规范与需求两个视角始终覆盖。按实际风险增加设计、性能、数据完整性或并发等视角，并为各审查者明确责任范围；可以由一个独立审查者分别核对，也可分派多个独立审查者。工具或协作规则无法支持独立审查时，按相同标准自查，并在交付中明确审查独立性的限制。

改动涉及默认值、校验、异常处理或恢复策略时，读取 [防御与设计原则](references/defensive-design.md)。需要深入追查防御、重复实现或职责划分时，可使用 review-code-design；没有安装也可按包内原则审查。

数据经常成组传递、同一规则的改动散落多处，或代码频繁操作其他模块内部数据时，按需读取 [设计问题线索](references/design-signals.md)，沿调用和改动后果核实，不仅凭代码形状报告问题。

改动包含已有测试的修改、删除、跳过或断言放宽，可能改变保护范围的快照、fixture、mock 调整，或新接口替代旧结构时，读取 [维护已有测试](references/test-maintenance.md)。核对需求依据、原风险的覆盖去向及替代保护的验证证据；缺少证据时指出具体风险，不仅凭测试通过接受覆盖变化。

- 规范：对照项目明文规则报告偏差，给出规则来源。命名、重复、过度抽象等设计迹象须说明具体维护后果，区分建议与硬性违规。
- 需求：检查缺失行为、实现偏差和未经要求的范围扩大，指出对应要求及受影响场景。新增代码并不自动等于范围扩大，必要的配套修改应结合目标判断。

各视角检查真实调用、错误路径、状态与兼容性，避免只看 diff 局部。合并发现时消除重复，保留每项所属视角，避免因一项通过而忽略另一项的缺口。复用已有专项审查的有效证据，补查本次变化与未覆盖边界。

## 报告与完成

每项可行动发现说明位置、触发条件、后果、证据和建议方向，可写成紧凑段落，不要求固定栏目；严重程度依据影响，推断须注明尚待核实的前提。共同背景只交代一次，检查项不逐项回显。优先验证高影响疑点，使用最小必要检查，不为形式完整运行无关测试。

交付按重要性排列的发现，同时分别交代规范与需求的结论，以及检查范围和未验证项。没有可靠发现时明确说未发现问题，并说明证据限制。实际变更已覆盖、关键风险已核查或清楚标明无法验证的原因后，审查完成；不默认保存报告、修改代码或发布评论。
