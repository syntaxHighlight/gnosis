# 设计问题线索

这些线索帮助选择追查方向，本身不是缺陷或违规。只追查与本次变更及其影响边界有关的部分；结合真实调用、领域含义和修改历史，说明当前改动会造成什么后果。没有充分证据时保留为问题或建议，不要求顺便重构。

| 线索 | 沿什么证据核实 | 何时值得报告 |
| --- | --- | --- |
| 多个值反复成组传递 | 它们是否共享含义、有效性约束和生命周期；调用者是否反复校验组合，或容易交换、遗漏其中一项。 | 组合约束散落或当前调用可构造无效组合，造成具体错误或维护负担时，考虑用已有领域类型或封装集中规则。仅在局部同时使用、生命周期不同或受外部协议约束的值不必强行打包。 |
| 同一规则的一次修改散落多处 | 多处修改是否确实源于同一业务决定；是否出现遗漏、分叉，或必须记住隐含的同步顺序。 | 已有或可说明的遗漏路径会导致行为不一致时，指出权威定义和应集中承担责任的边界。跨独立领域、信任边界或有意独立演进的规则不能仅因相似就合并。 |
| 一个模块反复读取并改写另一个模块的内部数据 | 调用者是否知道内部结构、状态约束和操作顺序；是否绕过拥有者维护的不变量，或因其内部变化而被迫跟改。 | 当前操作可能破坏约束，或具体变化需同步多处调用者时，考虑把行为移回数据与规则的拥有者。协调多个领域的应用流程、只读投影及明确公开的数据契约可以是合理边界。 |
| 分支、长函数或中转层使规则难以追踪 | 一次行为变化是否涉及多种职责，路径是否难以验证；中转层是否集中处理实际的协议、状态或错误语义。 | 能指出漏处理的路径、重复修改或理解依赖时，建议拆分或合并相应责任。行数、嵌套深度和转发本身不足以证明问题，移除层后也要判断复杂度是否只是散落到调用方。 |

说明应由哪个模块承担这项行为，以及调整的收益和边界。避免仅为符合某种模式引入新类型、接口或通用框架。发现真实缺陷时按影响报告；即使设计也有改进空间，修复仍可先于完整重构。
