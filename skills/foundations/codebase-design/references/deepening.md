# 依赖与验证

按真实依赖选择最小隔离方式，不预先要求所有依赖都通过端口隔离。

| 依赖 | 设计与验证考虑 |
| --- | --- |
| 进程内计算或状态 | 直接组合，通过模块行为验证；只有真实变化点才增加替换接口。 |
| 本地数据库、文件等 | 优先现成的隔离实例或适用的替代实现；检查事务、约束、时序等语义差异。 |
| 自有远程系统 | 让业务规则与传输协议分离，在测试中控制超时、重试和失败；保留验证真实协议的契约或集成检查。 |
| 第三方服务 | 在系统拥有的边缘封装协议及错误映射；测试替身验证己方处理，必要的外部契约检查补足其盲区。 |

使用替身的测试通过，只说明己方逻辑满足假设，不能证明外部服务满足这些假设。报告未覆盖的真实交互。

将调用方承担的规则、状态或错误处理移入模块后，按以下步骤迁移测试，防止新旧测试层不断叠加。

1. 将旧测试对应到其保护的行为、错误路径和风险，识别仅断言内部调用顺序或重复实现的部分。
2. 先在新接口建立行为测试，通过旧缺陷、受控扰动或独立预期证明测试能检测对应问题，并检查正常路径。
3. 新测试确实保护原风险后，移除已失去意义的实现耦合断言和重复覆盖。移除旧测试后运行受影响的测试入口，核对覆盖缺口。
4. 保留保护独特算法契约、协议边界、并发时序或重要诊断能力的低层测试。替身无法覆盖的真实协议和事务语义继续由契约或集成检查承担。

按行为价值决定保留、移动或删除，交付时说明重要覆盖迁移和剩余盲区。

修改接口时检查错误语义、生命周期、并发与调用顺序。先让旧调用者继续工作或提供明确迁移，再移除旧约定；局部性提升应能在真实调用差异中看见。
