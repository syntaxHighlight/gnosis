# 领域语言与决定

让需求、讨论和代码谈论同一个概念。仅阅读术语不需要启动完整建模；此技能用于概念或记录确实需要改变时。

先读取项目说明、术语表、上下文划分和 ADR。Gnosis 项目的术语表固定为 `GLOSSARY.md`，ADR 固定放在 `docs/adr/`。已有记录位于其他位置时，先读取现有内容，需要接入固定结构时使用 `setup-project` 的预览与确认流程，不自动移动文件。若存在术语映射，先定位适用上下文，同名概念在不同上下文可能含义不同，应记录差异与转换。

## 澄清概念

从具体场景说明概念的身份、生命周期、关系和边界。遇到“账户”“任务”等歧义词时，指出可能含义并提出精确名称。对照当前实现与用户期望，明确是术语冲突、实现缺陷还是计划中的变化；代码现状不是领域定义的唯一依据。

选择与当前概念有关的边界、失败和反例，主动检验定义。例如：属性改变或删除后重建，是否仍是同一个对象？状态转换失败、撤销或重试后，对象处于什么状态？关联对象缺失、替换或跨上下文时，关系是否仍成立？根据反例修正定义，或列出尚未解决的冲突。若未决选择会实质改变目标或行为契约，将其列为待确认问题；实现和文档写入仍限于已授权范围。

会在后续需求、代码或沟通中持续使用的概念，在定义敲定后及时进入术语表。每项写明规范名称、含义、适用边界及必要的反例或相关概念。多上下文中的同名词注明所属上下文，旧称和易混词指向规范名称。保持领域描述，接口细节和实施清单放到对应设计或规格。

## 记录决定

ADR 记录具有长期架构影响、未来需要保留理由或取舍的决定。判断重点包括模块及领域边界、数据所有权、跨模块协议、技术绑定、重要质量约束，以及偏离常规做法的选择。逆转成本高、脱离背景难理解和存在真实权衡都是重要信号，按决定的实际影响判断。

写入或更新 ADR 前，读取 [ADR 维护约定](references/decision-records.md)，按统一字段、状态及替代关系记录。实际备选、约束、理由和后果可以简短表达，未发生的权衡如实说明。短期排期或没有长期影响的实施细节保留在相应任务中。

在已授权的文档任务范围内更新记录，确有内容才创建文件。`setup-project` 已约定维护方式、当前任务也包含领域记录时，常规更新沿用该授权；只获准讨论时在对话中交付建议。文档事实与引用整理可交由 `maintain-docs` 辅助，术语定义和架构选择由领域讨论决定。

完成标准是关键概念能解释真实场景，冲突及未决项有明确归属，敲定的定义与决定已按授权记录，ADR 状态及历史关系一致。仅获准讨论时，关键概念的澄清已在对话中交付，冲突与未决项有明确归属即可完成，不要求写入记录。提交、推送和外部发布遵循已有授权。
