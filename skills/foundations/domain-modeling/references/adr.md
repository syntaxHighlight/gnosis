# ADR 条件与格式

## 判断是否记录

先判断决定是否会长期影响架构，以及未来读者是否需要保留它的理由或取舍。典型对象包括边界及数据所有权、跨模块协议、重要质量约束、难替换的技术选择、刻意偏离常规的做法。已经由其他有效记录完整解释的决定可以引用原记录。

逆转成本高、脱离背景令人意外、有真实备选都能支持建立 ADR。直观但影响深远的边界决定也可以记录。日常排期、局部实现细节和未形成决定的讨论放在任务、规格或访谈记录中。

## 默认格式

Gnosis 项目在 `docs/adr/` 使用顺序编号，例如 `0001-task-state.md`。编号取现有最大值加一，保存前再次检查，避免并行写入覆盖。项目已有编号规则时沿用现有规则。已完成迁移的项目使用迁移时确认的编号约定。

每份 ADR 至少包含下列信息，正文篇幅随决定调整。

```markdown
---
id: ADR-0001
date: YYYY-MM-DD
status: proposed
supersedes: []
superseded_by: null
---

# 任务状态与分诊状态独立表达

## 背景与约束

当前问题、需要满足的约束及决定的适用范围。

## 决定与理由

选定做法，以及支持它的事实和判断。

## 考虑过的备选

实际考虑过的方案及取舍。没有实质备选时如实说明。

## 后果与代价

收益、限制、迁移影响，以及需要继续验证的事项。
```

`id`、标题、日期、状态、背景、决定、理由、实际备选和后果应能找到。允许将相关正文合并成短段落，保留这些信息即可。`supersedes` 引用被本决定替代的 ADR ID；没有时为空列表。`superseded_by` 引用替代本决定的 ADR ID；没有时为 `null`。建立关系时同时提供可访问的文档链接。

## 状态与历史

- `proposed` 表示已形成候选决定，尚未获得接受。正文说明待确认事项。
- `accepted` 表示已接受并成为当前架构约束。接受日期与最初提出日期不同且值得追溯时，在正文记录。
- `rejected` 表示提案经过讨论后未被接受，保留拒绝理由及实际采用的决定入口。
- `deprecated` 表示明确废止，尚无替代决定。说明废止理由和影响。
- `superseded` 表示已被其他 ADR 替代，`superseded_by` 必须指向相应记录。

提案接受或拒绝时更新状态或在对应任务记录处理结论。已接受的决定发生实质变化时建立新 ADR，新记录引用旧记录，旧记录标记为被替代。旧背景、理由和当时的取舍继续保留。更正错别字和修复链接可以直接更新，避免借此改写历史决定。

当前配置的格式优先。迁移现有 ADR 时展示 ID、状态、路径和引用映射，按 `setup-project` 的确认流程处理，不将缺少新字段的历史记录直接判作无效决定。
