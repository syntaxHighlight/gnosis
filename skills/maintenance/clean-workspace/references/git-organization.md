# 未提交修改与提交历史整理

执行 Git 写操作前读取项目及运行时适用的 Git 工作流规则。授权来自用户请求和有效项目规则；已有授权内的步骤直接执行，配置、工具能力或整理建议本身不授予新权限。普通编辑不隐含提交，提交不隐含历史改写或推送。

## 核实现场与分组

1. 用只读命令确认仓库、当前分支/HEAD、工作树、暂存区、untracked 内容及相关差异。检查是否正在 merge、rebase、cherry-pick 或存在未解决冲突；已有操作未处理清楚前不叠加整理。
2. 结合实际 diff、任务和项目规则判断归属与意图，区分本次授权内容、他人或其他任务内容及未知项。记录原 HEAD、暂存与未暂存边界，以及需要保留的文件；不把所有暂存内容默认视为待提交内容。
3. 按可说明的行为或维护目的分组，纳入相应测试、文档和生成文件，识别依赖与提交顺序。每组应能解释且可验证；存在紧密依赖、无法独立成立的改动时合并成一个合理提交，不为提交数量强拆。
4. 核实项目的提交格式和验证入口。各组按其影响运行最小充分检查；最终工作树检查通过不能证明拆出的中间提交可用。必要时用隔离 worktree 验证提交树，避免误用主工作树中的未提交依赖。

## 未提交修改分组提交

用户仅请求分类时先交付分组和顺序；请求整理并提交时，在已授权范围内执行。

- 同一文件混合多个意图时按 hunk 选择性暂存；同一 hunk 仍有混合修改时，核对上下文后构造并检查精确的索引补丁，或在隔离环境拆分。不能为便于 `git add` 改写或丢弃无关工作树内容。无法可靠拆开时说明需合并的原因，范围或归属受影响时等待决定。
- 提交前对照基线检查完整 `git diff --cached`、路径和统计；确认其中只有当前组。已有暂存包含其他组或范围外修改时，不能连带提交，也不能擅自清空索引；优先用隔离工作树/索引或经授权的精确处理方式保留其内容与暂存边界。选择隔离方式时，提前确定提交如何安全接回当前分支；无法保留当前工作区状态时先给出具体方案。
- 每组验证须针对实际提交内容，检查依赖组已经提交，防止验证被未提交内容补齐。按项目约定写提交信息；无约定时使用 `<type>(<scope>): <summary>`，以简体中文祈使句概括意图。
- 每次提交后核对提交差异、提交标识以及剩余工作树和暂存区。完成后确认所有授权组均已处理，未纳入的修改仍保持原内容与预期暂存状态。操作失败时保留准确错误和现场，不用更激进的命令绕过。

## 整理已有提交历史

### 确定范围与恢复方式

先把“最近几次”“这个分支”等描述解析成准确 base、原 tip 和有序提交列表，核实祖先关系、与目标分支的分叉点、相关 diff 及 merge 提交。`base..tip` 的可达集合不必然是可线性重放的序列；不能凭固定 `HEAD~N` 或当前分支名猜范围。列清哪些提交保留、合并、重排或改写，确认范围外提交不会被带入。

检查本地 tracking、远端相关 ref 和协作证据是否足够新；按授权刷新必要状态。已发布、被其他分支依赖或他人正在基于其工作的历史，应说明受影响者和 ref，优先提出追加提交等不改写方案；只有已明确授权对应共享历史改写才执行。无法确认共享状态时说明不确定性，不能把没有 upstream 当作无人使用的证明。推送、force-push 和远程 PR 操作分别判断授权。

记录原 tip 和 base，并在改写前创建不会随分支移动的恢复 ref，说明其用途。核实 dirty state，包括 staged、unstaged 和 untracked 内容：能在隔离 worktree 中安全整理时优先隔离；必须改变当前工作区时，说明受影响内容并按已有明确授权的保护方案操作，没有方案才询问 stash、独立提交或取消。stash 必须核实收录范围并记录准确标识；恢复后核对内容与暂存边界，失败时保留 stash，不自动清除。恢复 ref 只保护已提交历史，不代替未提交内容保护。

### 执行与验证

- 依用户目标选择 squash/fixup、重排、拆分或改写提交信息，保留每组意图与依赖。仅整理历史时保持最终内容不变；如果需要修复业务内容，先说明并取得对应范围授权。
- 遇到 merge 历史，先核实父节点、拓扑及 merge 解决结果。明确选择保留拓扑的方式（如适用的 `rebase --rebase-merges`），或仅在已授权且理解后果时展平；普通线性 rebase 不能作为默认做法。无法可靠保留时停在方案，不自动删除 merge 或其冲突解决。
- 冲突时检查双方改动及原 merge 解决，不机械选择 ours/theirs，不跳过未知提交。保留正在进行的操作和恢复入口；需要中止时确认不会丢失尚未保存的冲突处理，不能自动 reset hard 清场。
- 完成后比较原 tip 与新 tip 的内容树；纯历史整理应有相同 tree 标识或无最终内容差异。核对新旧提交映射、消息、顺序、范围外历史和预期拓扑。内容树等价不能证明中间提交可用，重排、拆分或重新分组后按依赖和风险验证相关中间提交及最终状态；只改消息且树未变时可复用有效验证。
- 最后恢复并核对受保护的未提交内容及暂存状态，报告旧范围、新范围、验证、剩余修改和恢复 ref。恢复说明应结合当前状态给出安全路径；dirty state 未处理前不能建议直接硬重置。恢复材料保留到确认不再需要，清除它们另按授权与用途判断。

没有推送授权时，本地整理完成即可交付；推送授权也不自动包含 force-push。涉及远端历史替换时核对准确目标、预期远端 tip 及保护条件，不以历史整理授权代替明确的破坏性操作授权。
