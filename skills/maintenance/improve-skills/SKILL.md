# 改进技能

目标是使技能在真实请求下做出更可靠的决定。先确定待改技能与已观察的问题；没有失败样例时，可从用户目标和现有内容构造有代表性的使用场景，明确它们是评估用例。

## 复盘与定位

先读取本次相关对话、执行结果和可用日志，复原触发问题的场景。将候选原因分为指令、导航与信息、工具环境、自动检查、执行判断。机械规则优先考虑现有 lint、测试或校验器，反复找不到材料时检查发现入口，只有技能确实引导了错误行为时才修改技能。技能范围外的环境改进单独交付建议。

编写或调整代理指令前，读取 [指令设计](references/writing-for-agents.md)。按默认流程、分支选择、用户决策点与完成条件组织方法；简单技能可将这些内容合并为短流程。

读取技能、它实际依赖的资源及相关调用入口，检查触发是否过宽或过窄、边界是否冲突、完成条件能否判断、引用是否有效。区分文本缺陷、工具限制和环境缺失；不能用新增规则掩盖环境问题。

逐一检查技能处理的场景：何时应加载技能或参考文件，加载后能否找到所需方法。完成条件既要能检查，也要能发现遗漏；例如“给出故事列表”并不保证覆盖了各角色的关键诉求。

将问题写成可观察的行为差异，例如“单项修改被迫执行整个任务队列”或“缺少可选工具便停止交付”。确认该行为确由技能引导，而不是只因某一句话不合个人偏好。

## 修改与对照

1. 选择能改变问题行为的最小调整。优先替换、合并或删除含混和重复指令，避免在文件末尾不断叠加例外。精简或合并时，检查关键动作、输出要求、覆盖检查和帮助判断的示例是否仍有保留。用原则替代具体方法前，先用场景确认它仍能引导同一行为。保留用户的选择和授权边界。
2. 保持描述、正文与资源分工一致：描述负责何时使用，正文给目标与关键判断，分支细节按需引用。单独安装时具备必要能力，其他技能或工具缺失时说明可行退路。
3. 用同一请求和原始材料比较修改前后的行为，检查目标问题及相邻正常用法。按复杂度选择实际试运行或明确标注的静态推演；两者不能混称。评估在隔离目录完成，只执行其授权范围内的动作。
4. 检查 frontmatter、命名、引用及新增脚本。脚本有变动时验证实际行为；有现成校验器时使用它，结果不代替行为对照。

评估材料需要保存时读取 [产物约定](references/artifacts.md)。普通修订不要求建立长期记录；保留有复用价值的场景，而非整段对话转录。

## 完成标准

报告原问题、关键改动、行为对照方式与结果，以及仍未验证的分支。若证据不足以支持改动，可交付问题与所需输入；不为凑修改而重写。技能修订不自动授权安装到全局目录、升级依赖、提交或发布。
