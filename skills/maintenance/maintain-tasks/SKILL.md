# 维护任务记录

让记录准确表达已决定的工作、执行顺序和真实进展。先确定用户请求是建单、去重、排序还是校正状态，只修改对应范围。

原始请求是否成立、信息是否足够及分诊状态由 triage 判断；已决定目标的交付切片由 to-spec 设计。本技能依据这些结论维护记录，YAML 字段和引用交给 tracker 校验器核对。说明文档的内容同步由 maintain-docs 处理，各步骤引用同一项决定和验收证据。

涉及 tracker 读写时，先读取 [tracker 约定](references/tracker.md)。已有系统、字段和状态约定优先；`.gnosis/project.json` 可提供配置，但不是运行前提。外部 tracker 的写入需要相应授权；本地记录不能冒充外部系统已更新。

## 整理内容

- 读取请求、来源材料和相关现有任务，按具体目标去重。原始反馈中的事实与建议分别处理；尚未确认的问题可以记录待核实内容，不能写成已确认缺陷。
- 一项任务对应可单独说明和验证的结果，包含上下文、目标、验收条件和验证方式。共享前置工作使用依赖，目标归属使用父子关系。
- 合并重复任务时保留来源、独有条件和历史引用。重排只改变选择顺序，依赖仍优先；不能通过排序消除阻塞。
- 状态依据实际进展和证据。受阻项说明阻塞原因及解除条件；完成项对应验收结果；取消项保留取消理由与对其他任务的影响。

本地记录字段、分类和分诊状态遵循 tracker 约定。沿用稳定 ID，保留已有分诊结论；执行状态变化并不自动改变请求的分类或分诊状态。字段矛盾需根据来源澄清，不能靠改标签消除真实依赖。

## 核对与交付

核对 ID 唯一、引用存在、依赖无环、父子关系无环，且状态与验收证据一致。上层目标不能仅靠子项数量自动完成，还需检查自身条件。记录需要归档时按项目现有方式保留历史；涉及独立材料时读取 [产物约定](references/artifacts.md)。

关闭 tickets 或 spec 前逐项对照验收。内部 checklist 只勾选已满足且有证据的条件，未验证和用户尚未决定的事项保持开放。取消部分范围时记录用户决定和对父目标的影响；父 spec 还需满足整体行为与集成条件。外部关闭按已获授权执行，报告实际状态。

报告新增、合并、重排和状态变化，以及未解决的矛盾。维护记录不隐含实现代码、提交、关闭外部 issue 或执行全部待办。
