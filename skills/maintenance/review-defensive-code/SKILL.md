# 审查防御代码

读取 [防御与设计原则](references/defensive-design.md)，检查防御代码在处理什么失败、由谁负责，以及调用者能否得到正确的结果。根据证据建议保留、加强或调整。

## 确定范围

按用户指定的文件、模块、变更或提交范围审查。审查 diff 时固定比较基点，结合相关调用者和既有改动阅读。用户未指定范围时，从当前任务或近期改动定位；仍无法确定再询问。读取相关项目规则、规格、类型、测试和设计决定。

沿调用链查清为什么需要这处防御，必要时检查接口和模块划分。范围之外的架构问题留待后续调查。可用时参考 codebase-design；独立安装时使用包内原则。

## 核实疑点

查清输入从哪里来、哪些条件已由谁保证，以及执行到当前分支时这些保证是否仍然成立。继续追踪防御触发后调用者实际收到的结果。

留意吞掉异常后返回正常值、用默认值掩盖必填数据缺失、重复校验同一条件、没有停止条件或可能重复产生副作用的重试，以及用途不明的兼容分支。逐项核实后再判断是否有问题。检查正常、失败和恢复时的行为；移除防御可能改变公开行为时，查找依赖它的调用者和测试。

通过阅读代码或最小验证核实疑点。可以运行已有且无外部副作用的检查。若验证需要额外权限、写入或向生产环境注入故障，说明还缺什么证据，不执行这些操作。

如果含糊的接口、容易构造的无效状态或分散的责任导致了这些防御，解释其中的关系。建议应说明能改善什么行为或减少什么维护负担；写法、行数和模式名称不足以证明设计有问题。

## 报告与完成

默认在对话中报告。用户要求文件时，按 [产物约定](references/artifacts.md) 保存到指定位置或项目报告目录；可用 present-report 辅助呈现。

将已确认的问题按影响排列，说明位置、触发场景、违反的契约和后果。给出建议时，一并说明调整后的行为和验证办法。待核实项单独列出；需要解释取舍时，也说明哪些防御应保留或加强。

范围内的疑点都已核实，或已说明缺少的证据，即可完成审查。交代审查覆盖了哪里、如何验证、还有哪些未验证；没有确认的问题就如实说明。只交付报告，不修改被审项目、配置或任务记录，不创建或发布 spec、ticket。由用户决定后续工作。
