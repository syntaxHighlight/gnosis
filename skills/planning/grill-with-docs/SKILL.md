# 访谈与领域记录

通过追问厘清方案，只把未来读者仍会用到的知识写入项目文档。访谈本身不是规格生成或实现任务。

本技能依赖 `grill-me` 和 `domain-modeling`。开始前读取两者的 SKILL.md，分别使用访谈决策树与领域建模方法，本文件组织讨论和记录的衔接。缺少必要技能时，说明需要一并安装的依赖及当前可继续处理的部分。

访谈前读取项目说明及影响讨论的术语表与 ADR；固定位置见下文，已有其他位置的记录也须核对。已通过 `setup-project` 确定文档维护方式，且用户请求本次带记录的访谈时，按该约定持续更新；位置或授权有实质歧义时先明确缺口，其余讨论可以继续。

随着定义和决定敲定及时记录，避免访谈结束后从长对话重新推断共识。术语表固定为 `GLOSSARY.md`，ADR 固定放在 `docs/adr/`，格式沿用项目约定；已有其他位置的记录时按 `domain-modeling` 核对接入与迁移，确有内容才创建文件。

- 领域术语应持续出现在需求、代码或协作中。定义敲定后更新规范名称、含义、边界和易混概念，短期工作名和实现细节留在对话中。
- 形成或更新架构决定记录前，读取 [ADR 维护约定](references/decision-records.md)，按 `domain-modeling` 的条件形成 ADR。已确认的决定记录为接受状态，需要保留的备选或未决决定记录为提案状态，并写清尚待决定的内容。

术语冲突先展示不同含义，试探中的说法保留为待定。已有 ADR 被新决定替代时，保留历史并建立关联。记录写入后继续下一轮访谈；访谈中只更新内容，不调整文档结构。结束后如需整理结构，由用户另行触发 `maintain-docs`。仅需说明整理方向时，若 `maintain-docs` 可用，读取其 SKILL.md 并据此建议；未安装时直接建议。领域含义及决定仍由本次讨论与 `domain-modeling` 确定。

收束时汇总关键结论、未决项和实际修改的文档。完成标准是重要分歧已处理且有持续价值的记录准确反映结论；没有值得长期保存的内容时，纯对话也是完成。此技能不授予范围外写入、提交、推送或发布权限。
