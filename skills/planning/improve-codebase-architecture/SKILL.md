# 寻找值得做的架构改进

从实际修改成本出发，寻找通过清晰接口集中分散知识的机会。用户指定模块或痛点时按该范围调查；否则用近期变更、缺陷或调用热点选择入口。读取相关术语和设计记录，尊重已知约束。

可用时参考 `codebase-design`；独立使用时以以下标准判断：接口包含调用者必须理解的参数、顺序、错误和约束；好的模块把复杂行为封装在易用接口后，让相关变化集中。少文件、少行数或多一层抽象本身不是改善证据。

沿真实调用路径寻找重复规则、泄漏的状态、难以通过行为验证的耦合和跨模块改动。对每个候选核实代码位置、受影响调用者与实际后果。设想去掉现有抽象：复杂度会消失、转移还是散落回调用方？据此判断该合并、重划接口还是保留结构。

## 展示可比较的候选

先简列有证据的候选及优先判断，数量由证据决定，不凑数量；没有值得做的改进也可明确报告。只对值得优先处理或进一步核实的候选展开，说明涉及的位置、已观察到的修改障碍、改进方向、收益、迁移及验证风险、证据强度。共同背景只交代一次，不为每个候选重复。

用文字说明调用者需要知道什么、复杂行为放在哪里；关系难以用文字讲清时再用前后关系图。图不能把尚未验证的推断表现成现状。

制作候选图示时，读取 [候选呈现示例](references/candidate-example.md)，用同一场景比较前后责任与验证接口，避免只展示文件数量变化。

需要报告文件时先读 [产物约定](references/artifacts.md)，放入工作区 `reports/` 并返回可打开路径。可使用 CDN，但说明在线资源依赖；关键文字和关系在脚本不可用时仍应可读。按问题选择 Mermaid、SVG 或 HTML，避免为视觉效果掩盖不确定性。

给出优先建议与理由，交由用户选择深入方向。若候选违背现有决定，明确新证据为何足以重新讨论。用户选择后，可用 `grill-me` 追问关键权衡；没有该技能时自行讨论约束、接口、依赖与验证策略。接口尚未达成共识时保持为候选。

完成标准是候选有可追溯证据、前后变化可理解、用户能够选择下一步。生成报告不授权改代码、创建 ADR、提交或发布；持久化领域决定需另有相应任务范围。
