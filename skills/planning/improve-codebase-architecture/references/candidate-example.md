# 候选呈现示例

下面是虚构示例，用于说明值得展开的候选应提供的证据和比较粒度。报告先展示推荐、主要收益和待决定问题，再让读者进入比较和证据。真实报告中的位置、问题与收益来自调查，尚待验证的部分明确标为假设。

**候选：集中订单取消规则。** 假设已查到网页入口和后台作业各自判断取消资格、释放预留，并安排退款；最近两次规则修改都改了两条路径，且一次漏改后台作业。

| 比较项 | 当前 | 候选方案 |
| --- | --- | --- |
| 调用者需要知道什么 | 每个入口了解资格判断、预留释放和退款顺序 | 入口提交取消意图并处理明确结果 |
| 业务规则在哪里 | 两条入口分别编排取消流程 | 取消模块负责规则和流程，外部协议留在适配器 |
| 如何证明行为 | 两条入口各自测试，重复规则仍可能漂移 | 在取消接口验证规则；保留入口接线与外部协议检查 |
| 尚未解决什么 | 失败后可能只完成部分步骤 | 需要明确事务、退款失败恢复和重复请求语义；合并文件不会自行解决这些问题 |

对这个候选，可以比较三个方向。

| 方案 | 预期收益 | 代价与验证 |
| --- | --- | --- |
| 保持两条独立流程 | 无迁移成本，适合契约实际不同的情况 | 继续维护重复规则，核实是否确实需要独立演进 |
| 提取共享取消规则 | 小范围集中资格与金额计算 | 编排仍重复，用两入口的相同场景验证规则一致性 |
| 合并取消能力与状态转换 | 将取消、预留和退款顺序集中到一个行为接口 | 明确事务与补偿，验证重复请求、部分失败和外部协议 |

重要结构方案提供前后图。前后两侧保留同一组入口和外部依赖，让读者看见规则从哪里移到哪里；标注拟议接口及未验证的恢复路径。多个方案采用相同粒度，每幅图突出责任变化，避免堆入全部文件和方法。更小的方框不代表已测得维护成本下降。

首屏可以给出“优先验证共享取消契约，再选择提取规则或合并能力”，让读者知道当前建议及决策条件。比较表、前后图紧随其后，具体代码位置、历史缺陷、迁移步骤和详细测试场景放入可展开部分。读者先能判断值得看什么，再按需要追溯依据。

简列时说明候选是优先处理、值得进一步核实，还是仅为假设，并附上简要判断依据；只有值得展开的候选才补充上述比较。需要进一步核实时指出下一步要查清什么，例如两个入口是否确实共享同一取消契约。没有真实重复规则时，保留独立流程可能更合适。
