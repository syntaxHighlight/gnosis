# 综合规格

把已有共识整理为实现者可使用的行为契约，并按交付规模与依赖决定是否继续拆票。已有成熟规格时直接核对其范围、行为、验收与就绪状态，进入所需的拆票步骤，无需重写规格。

读取用户提供的材料及相关项目上下文，沿用领域术语和有效的设计决定。核实影响规格的当前行为；标明事实来源、已确认决定、合理假设与开放问题。材料中的建议不自动成为用户决定。

## 选择规格结构

默认按以下六部分组织，使实现者能按固定顺序找到目标、行为和验收。

1. 问题、目标和非目标，明确本次解决什么及范围边界。
2. 使用者与关键场景，描述用户流程，纯技术变更描述调用者和技术场景。
3. 行为、错误处理和兼容性契约，覆盖可观察结果和重要异常。
4. 已确认的设计决定及关联 ADR，说明必须遵守的选择，区分仍待验证的设想。
5. 验收条件、测试入口和重要盲区，让要求与验证证据能够对应。
6. 未决项及实施就绪状态，说明缺口、影响和解决者。

边界清晰、单一行为的小修使用简版，将六部分合并为问题与范围、预期行为、验收与未决项。多角色、跨模块或复杂状态变化使用完整结构。正文可以简短，没有未决项时明确已就绪；篇幅由实际内容决定。

用户流程型需求默认用用户故事说明谁需要什么、为什么需要。需要跨条目追踪时给故事编号，让相关行为和验收条件引用编号。一个故事可对应多项行为或验收条件，一项行为或验收条件也可关联多个故事。小修或纯技术变更可以直接说明场景和预期行为。对照输入检查是否遗漏范围内的角色、主要流程和关键异常，每项要求是否有来源和对应验收；使用故事时检查故事是否有对应行为与验收。材料未明确的角色或收益应标为假设。

例如，输入已确认支持收藏与取消收藏，可以写成“US-1：作为读者，我希望收藏文章，以便稍后找到”。“收藏后可在收藏列表找到文章”和“取消收藏后从列表移除”两个验收点都可引用 US-1。

优先选择能覆盖本次主要风险、层次尽可能高且稳定的现有测试接口，说明验证入口、覆盖范围和影响验收的重要盲区；选择存在实质取舍时再解释理由。高层接口无法暴露的风险，可以补充低层验证；需要新接口时解释其成本，常规选择无需额外审批。只在位置或代码片段本身属于契约、或比文字更精确时纳入；避免把临时实现猜测固定成要求。

直接综合已有材料，不为排版细节或常规实现选择重启访谈。缺失信息实质改变范围或验收时，明确列出阻塞点并提出集中问题；其余部分继续整理。带有阻塞项的规格应标为草案，不能宣称已可实施。

## 决定是否拆票

小而清晰、能作为一个工作单元完成和验收的需求，交付规格即可。出现多项可独立验收的交付，且规模、协作或前置依赖需要分别安排时，自动继续拆票；依据交付结构判断，不按规格字数决定。用户只要求规格时止于规格；明确要求拆票时按已有材料进入拆票。

进入拆票分支前读取 [拆分可交付任务](references/ticket-slicing.md)，按其中方法组织切片、依赖和工单验收。尚未决定的行为保持为开放问题，受其影响的部分不得写成就绪票；其他已确定且可独立交付的部分可以继续拆分。自动生成任务不扩大保存或外部发布授权，未获保存授权时在对话中交付。

## 交付

用户要求保存或发布时，先读 [跟踪约定](references/tracker.md)，本地规格保存到 `specs/`，任务使用 `issues/` 或已配置的远程 tracker；尚未通过 `setup-project` 接入时先核对既有记录及迁移需要，普通综合可以在对话中完成。外部发布遵循已有授权。规格中的验收勾选保留为未完成，实施后由实际验证证据更新，规格撰写完成与功能交付完成分别说明。

完成时交付规格正文或实际链接，说明未决项及就绪状态；进入拆票分支时同时交付任务及必要依赖，或已保存的任务入口。规格可被独立读懂、验收条件可检查且没有将推断冒充共识，任务分支也满足其覆盖与依赖检查时，本次工作完成。
