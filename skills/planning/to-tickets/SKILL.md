# 拆分可交付任务

把已确定的目标变成可执行的工作图。`triage` 负责核实未决请求和判断实施就绪程度，本技能处理已经确定的交付目标。任务记录的合并、状态及依赖维护由 `maintain-tasks` 负责；`maintain-docs` 负责同步受影响文档的事实与引用。需要文档交付时将其纳入相应票的验收，规模足够且可单独验证时再独立成票。

读取输入及关联讨论，定位相关实现、结构摩擦和验证方式。先读 [跟踪约定](references/tracker.md)，使用 setup 确定的任务位置、字段及标签映射。尚未配置时可先形成拆分草案，已有记录的迁移按 setup 流程处理。

## 切片与依赖

先按当前结构和交付约束选择切分路线，说明选择依据。

| 路线 | 适用条件 | 交付组织 |
| --- | --- | --- |
| 直接纵向切片 | 现有结构支持行为逐步成立 | 每片贯穿所需层次，形成可观察结果 |
| 准备性重构后切片 | 结构将导致重复修改、验证困难、冲突或不必要成本 | 先建立必要结构，再让后续行为票依赖其产物 |
| 扩展—迁移—收缩 | 共享契约、数据或调用者需要分批转换 | 引入兼容形式，迁移使用方，最终移除旧形式 |
| 联合交付并集中验收 | 中间状态无法独立成立 | 明确联合边界、中间完成含义及最终集成验收 |

默认优先纵向行为窄片；结构摩擦明显时主动评估准备性重构。重构的收益可以是降低风险、减少后续工作、改善验证能力、消除重复规则或建立必要边界。单独的重构票写明收益、行为保持要求、验证方式和使用其产物的下游任务。性能或架构改进本身就是目标时，重构可以成为主要交付。

每片说明结果、验收和必要上下文，范围有歧义时明确非目标。任务大小以能够在合理工作单元内完成并验证为准；跨层仅覆盖交付实际所需的层次。按真实收益选择路线，纯改名或顺手整理不能凭“重构”名称成为前置依赖。

逐票检查：没有读过本轮对话的新会话，能否仅凭工单和其中可访问的引用，理解为什么做、交付什么、现状与约束、如何验收，以及前置任务会提供什么。补齐影响实施的信息；已有稳定规格可以引用具体位置，无需整份复制。“如上讨论”不能代替必要上下文，小任务用几句交代清楚即可。

只记录真实前置依赖，没有对方结果就无法完成当前交付才构成阻塞，共享目录或相同技术不自动产生顺序。依赖图必须无环，引用必须可解析，入口任务能够立即开始。`parent` 表达归属，`depends_on` 表达阻塞。已在 tracker 建立的分诊标签沿用其含义，可实施票的执行依赖仍需单独满足。

跨库重命名和共享契约迁移优先检查扩展—迁移—收缩是否可行。联合交付时，工单明确哪些中间产物仅在集成后成立，避免将中间完成误报为独立可发布。

## 交付

先使切片及依赖可审阅。用户已明确范围和拆分偏好时直接执行获准的保存；关键范围未定时先交付可用草案并询问该分歧。用户要求先确认拆分时等待答复。

本地任务按跟踪约定使用 Markdown 与 YAML frontmatter，包含稳定 ID、标题、执行状态、依赖和归属；新任务通常为 `todo`，可选分类及分诊字段遵循 tracker schema。发布到外部跟踪器时使用项目配置的关系能力和标签映射，并遵守已有发布授权。拆票完成后保留父任务和规格的真实状态，后续实施根据各自验收证据更新勾选并关闭。

交付前检查每个验收点有归属、无重复任务、依赖无环，且未将尚未决定的行为伪装为可直接实施的票。核对过程无需逐项回显。

未保存时直接交付任务及必要依赖；已保存时返回入口链接、任务数量、关键依赖和实际未解决项，无需再完整列出文件中的任务。用户要求完整列表时提供。列表中的公共验收或状态规则集中说明一次，每项仅补充独有条件。
