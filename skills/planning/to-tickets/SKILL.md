# 拆分可交付任务

把已确定的目标变成可执行的工作图。此技能组织交付顺序，不替用户补作影响目标的产品决定，也不开始实现。

读取输入及关联讨论，必要时定位实现和验证方式。先读 [跟踪约定](references/tracker.md)；现有项目格式优先，`.gnosis/project.json` 为可选配置，缺少配置无需先 setup。

## 切片与依赖

优先按可观察行为切出贯穿所需层次的窄片，每片说明交付结果、验收、必要上下文和明确非目标。任务大小以能在合理工作单元内完成并验证为准，不按文件数量或固定票数拆分。

逐票检查：没有读过本轮对话的新会话，能否仅凭工单和其中可访问的引用，理解为什么做、交付什么、现状与约束、如何验收，以及前置任务会提供什么。补齐影响实施的信息；已有稳定规格可以引用具体位置，无需整份复制。“如上讨论”不能代替必要上下文，小任务用几句交代清楚即可。

只记录真实前置依赖：没有对方结果就无法完成当前交付才构成阻塞；共享目录或相同技术不自动产生顺序。依赖图必须无环，引用必须可解析，入口任务能够立即开始。准备性重构仅在它确实降低当前交付风险时单独列出。

跨库重命名、共享契约迁移等无法逐片保持兼容的工作，考虑先加入兼容形式、分批迁移、最后移除旧形式。确需联合交付时明确集成边界与最终验证任务，不能声称每片已独立可发布。

## 交付

先使切片及依赖可审阅。用户已明确范围和拆分偏好时直接执行获准的保存；关键范围未定时先交付可用草案并询问该分歧。用户要求先确认拆分时等待答复。

本地任务按跟踪约定使用 Markdown 与 YAML frontmatter，包含 `id`、`title`、`status`、`depends_on`、`parent`；新任务通常为 `todo`，依赖用稳定标识。发布到外部跟踪器时使用现有项目关系能力，并遵守已有发布授权。不默认修改或关闭父任务。

完成时返回任务列表、依赖关系、保存位置及未解决项。检查每个验收点有归属、无重复任务、依赖无环，且未将尚未决定的行为伪装为可直接实施的票。
