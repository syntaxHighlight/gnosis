# 请求分诊

将原始反馈推进到有依据的处理决定。先读取 [tracker 约定](references/tracker.md)，确认请求来源、项目分类和分诊映射。请求分诊负责内容判断，`maintain-tasks` 负责记录、依赖与状态维护，`to-tickets` 负责将已决定目标拆分成交付任务。YAML 字段校验交给 tracker 工具。

## 建立事实

1. 读取请求正文、讨论、既有分诊结论和相关实现。PR 还需读取完整差异，明确后续是补全、修正还是评审已有代码。继承已经解决的问题，避免重复询问。
2. 按领域概念查找已有实现、相似请求、术语表及相关 ADR，区分重复请求、已经实现、先前拒绝和暂缓。既有决定有新的前提变化时，提出重新判断的依据。
3. 对缺陷使用报告中的入口验证，记录环境、输入和结果。难复现时区分已确认事实和剩余假设，必要时使用 `diagnosing-bugs`。对改进核实当前能力和实际缺口，对 PR 核对声明与行为。只读分析不能冒充实际运行验证。
4. 给出分类、建议分诊状态、证据和待决定项。需要产品或架构决定时集中提问，复用 `grill-me` 的决策树与 `domain-modeling` 的术语和 ADR 方法；缺少辅助技能时仍可就具体缺口提问。

## 选择分诊结果

本地 `category` 取 `bug | enhancement`，`triage` 使用下表中的单一值。远程使用配置的标签映射。它们与执行 `status` 分别记录，`ready-for-agent` 说明内容就绪，任务是否可开始仍由执行状态和依赖决定。

| 分诊状态 | 进入条件及后续 |
| --- | --- |
| `needs-triage` | 尚未完成判断，记录现有证据和下一项核实工作 |
| `needs-info` | 缺少会改变判断的信息，列出具体问题、材料和回答者 |
| `ready-for-agent` | 范围、行为和验收已明确，形成可独立使用的执行说明 |
| `ready-for-human` | 明确需要人的判断、访问或操作，说明人工步骤和完成条件 |
| `wontfix` | 用户或项目已有决定拒绝处理，记录理由和适用前提 |

新请求通常从 `needs-triage` 开始。`needs-info` 获得新回复后回到判断阶段。用户明确指定结果时按其指令处理，指出与现有事实的实质矛盾；普通状态转换无需重复确认已授权的决定。

执行状态依据实际工作更新。等待信息只有确实阻塞执行时才是 `blocked`，拒绝实施后按决定标为 `cancelled`。已经实现的请求核实验收证据后记录完成，重复请求关联权威任务并保留原因，避免把已有能力记成拒绝的功能。

## 形成可交接说明

就绪说明包含请求来源、现状与已验证事实、期望行为、边界和已作决定、可检查验收、验证入口及重要未知项。PR 说明突出已有差异和剩余工作。引用稳定规格、ADR 和当前实现入口，附上必要上下文，使新会话可以独立继续。只为理解或定位提供路径，验收以行为为准。

尚待信息时，保留已经明确的内容并提出可回答的问题。拒绝请求时引用实际决定及理由；重复出现且有长期价值的范围决定纳入项目已有决定记录，避免另建平行的事实来源。批量分诊先汇总需要关注的请求、数量及简要原因，按用户选择或已授权范围处理。

写入标签、评论和关闭外部请求需处于已有授权范围。使用项目要求的自动生成标识。只读分诊可以交付建议和草稿，准确说明实际写入结果；关闭请求、完成 spec 和验收勾选分别依据对应条件。

分诊完成时，请求已有明确处理结果，或具体的待补信息及其解除条件；就绪说明可独立理解，状态与证据一致。报告决定、依据、实际记录变化和剩余事项。
